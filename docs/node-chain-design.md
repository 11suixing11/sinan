# 代理节点与多条链路设计

状态：规划完成，尚未实现。日期：2026-10-01。核对基线：`042409039cdfb0379cc0192a5105d00455697b7c`。

用户要求“创建的多条链路，应该在代理节点里面创建”。本方案将直连节点和两跳链路统一放到 **sing-box 插件 → 代理节点** 创建、查看和管理。多条链路可以使用同一台入口服务器，各自拥有独立监听端口、授权资源和订阅项。策略组引用这些资源，套餐定义用户自己的额度、周期与期限。

用户已确认采用“统一代理节点页面，直连节点和链路并列管理”，据此确定页面结构。

这里的“代理节点”指用户可以连接的业务资源；服务器是承载资源的设备。页面归属与两跳语义按本方案调整，分层、授权并集、不可变账本与协议边界继续遵循 [ADR 0035](adr/0035-singbox-policy-package-groups.md)。本文件描述目标行为，现有页面和接口的实际使用见 [策略与套餐说明](singbox-groups.md)。

## 现状与需要改变的行为

| 当前实现 | 目标行为 |
| --- | --- |
| [Groups.tsx](../web/src/plugins/singbox/Groups.tsx) 的第三个页签创建、列出和删除链路 | 代理节点页完成链路的全部管理操作；策略页选择已有资源 |
| [Nodes.tsx](../web/src/plugins/singbox/Nodes.tsx) 只读取节点，链路入口表现为普通节点 | 一条链路显示为一个两跳资源，清楚显示入口和出口 |
| 创建链路前要分别创建入口、出口节点 | 在链路表单中直接创建专用入口，选择已有出口；提交时一起保存 |
| 链路表单仅按 Reality 协议过滤候选 | 展示入口占用、既有授权、服务器和出口资格；提交时后端重新检查 |
| `available` 仅判断资源和协议是否存在 | 分别展示资源、授权、设备在线和配置应用状态 |

后端已经支持多条两跳链路：[迁移 0016](../crates/panel/migrations/0016_singbox_groups.sql) 限定一个入口节点只属于一条链路，[编译器](../crates/compiler/src/relays.rs) 按入口监听路由。这个约束保证用户选择的链路拥有确定出口，继续保留。

## 页面结构

```text
sing-box 插件
├─ 代理节点
│  ├─ 全部资源 / 直连节点 / 两跳链路
│  ├─ 创建节点：直连节点 / 两跳链路
│  └─ 资源详情：公开接入参数、拓扑、授权引用、两端配置状态、流量
├─ 策略与套餐
│  ├─ 策略组：选择已创建的直连节点、两跳链路
│  └─ 套餐组：流量额度、重置规则、有效期
└─ 代理用户
   └─ 分配策略组及套餐，查看授权来源和用量
```

代理节点列表按类型和服务器筛选。服务器筛选可选择“作为入口”“作为出口”“任一端”；直连节点按所在服务器匹配。链路详情使用 `/#/plugins/sing-box/nodes/chain/{id}`，直连详情使用 `/#/plugins/sing-box/nodes/direct/{id}`，导航均归属“代理节点”。节点 ID 与链路 ID 可以相同，列表、深链接和操作必须携带类型。

链路入口从直连资源列表和单独授权选择器中排除。出口节点可继续作为直连资源出现，并标注“被 N 条链路引用”。统计分别显示直连资源数和链路数；物理监听数、服务器数另行统计，避免将一条链路的入口、出口和链路重复计为三个用户资源。

策略组资源选择器将直连与两跳并列展示，保存时仍映射到既有 `node_ids`、`chain_ids`。没有链路时显示“前往代理节点创建链路”，并保留当前策略表单草稿。“策略与套餐”移除链路 CRUD 页签；旧入口引导至代理节点的链路筛选。现有旧链路页签没有独立 URL，无需新增假重定向。

## 在代理节点内创建一条或多条链路

默认流程如下：

1. 点击“创建节点”，选择“两跳链路”。
2. 选择入口服务器，填写客户端连接的公开地址、Reality 参数；端口可留空自动分配。
3. 选择另一台服务器上的 Reality 出口节点。多选出口时展开多行预览，每行有名称、入口端口和出口；也可以逐行添加相同出口。
4. 确认每行“客户端 → 入口服务器:端口 → 出口节点 → 互联网”，一次提交。
5. 返回创建结果，资源显示“未授权”。点击“加入策略组”只是进入明确的授权操作，不在创建时自动给既有用户授予权限。

示例使用同一台入口服务器：

| 代理资源 | 独立入口 | 出口 | 用户订阅 |
| --- | --- | --- | --- |
| 入口 A → 出口 B | A:20001 | B 节点 | 独立的一项 |
| 入口 A → 出口 C | A:20002 | C 节点 | 独立的一项 |
| 入口 A → 出口 D | A:20003 | D 节点 | 独立的一项 |

每行产生一个入口节点和一条链路。入口服务器可共用，出口节点也可共用；入口节点和监听端口必须独立。用户获得几条链路由策略组明确决定，客户端选择哪一项就使用那一项的固定出口。这里不增加自动出口池、随机出口或任意多跳。

兼容已有未授权入口时，在单行创建中提供“使用已有入口节点”。该节点必须为 Reality、没有任何用户授权或普通策略组引用、没有现有链路入口或出口身份。提交前明确提示“此入口将作为该链路的专用入口管理”；批量新建默认生成独立入口，不复用同一个旧监听。

端口留空时，预览显示“提交时自动分配”；预览不预占端口。最终端口在事务锁内分配，创建结果显示实际地址，避免并发创建导致预览与真实监听不一致。

入口和出口必须属于两台未退役且已启用插件的服务器。设备离线可以保存合法配置，但显示“等待设备上线应用”。没有合适出口时，在代理节点范围内创建出口节点，保留链路草稿；出口创建是用户明确创建的独立资源。链路提交失败时不遗留新入口。前端候选过滤只是操作提示，不能代替后端并发校验。

## 后端资源模型与接口

保留 `nodes`、`singbox_chains` 和现有授权表，以插件内统一资源投影连接产品页面。资源键使用 `node:<node_id>` 或 `chain:<chain_id>`。直连行保留节点名称，链路行保留 `chain.name`，两端的原节点名称单独展示；旧订阅中的入口名称不因页面迁移隐式重写。

所有新增接口位于 `/api/plugins/sing-box`，沿用管理员会话及请求安全校验。以下为**待实现接口**，不修改现有 API 文档为已上线行为：

| 接口 | 目标用途 |
| --- | --- |
| `GET /proxy-resources` | 同一数据库快照读取直连/链路投影、公开拓扑、引用和状态；保留破损链路供清理 |
| `GET /proxy-resources/{kind}/{id}` | 资源详情；`kind` 为 `direct` 或 `chain` |
| `POST /chains/batch` | 单条或多条原子创建，包含新建入口或合格已有入口以及幂等键 |
| `PATCH /proxy-resources/{kind}/{id}` | 编辑名称和允许的公开入口参数，拓扑绑定保持不可变 |
| `DELETE /proxy-resources/{kind}/{id}` | 按资源语义检查引用并删除；链路和专用入口一起退役 |

资源投影只含公开字段、节点/链路标识和状态；不返回 Reality 私钥、用户 UUID、内部 relay UUID 或完整部署配置。需要凭据的既有订阅仍经过当前资格检查。已有 `/nodes`、`/chains` 与策略接口继续兼容，新的管理页面使用统一资源接口。旧 `DELETE /chains/{id}` 的解除关系行为与新的“删除代理资源”明确区分，新页面不调用旧接口来删除整条资源。

直连创建继续调用既有 `POST /nodes`；链路创建调用新批量接口，单条也是一行请求。读取、编辑和删除使用统一资源接口，避免为直连重复新增一套创建逻辑。统一编辑接口内部复用现有节点校验，不跳过协议、证书和同服务器配置约束。

批量请求示例：

```json
{
  "request_id": "<本次提交的 UUID>",
  "items": [
    {
      "name": "入口 A → 出口 B",
      "entry": {
        "mode": "new",
        "server_id": 1,
        "public_host": "entry.example.com",
        "sni": "www.example.com",
        "port": null
      },
      "exit_node_id": 2
    }
  ]
}
```

新建入口的名称默认取本行链路名称，协议固定为 Reality；使用既有的密钥和 short ID 生成、端口校验以及服务器配置校验。复用入口使用 `entry: {"mode":"existing","node_id":1}`，与新建字段互斥。一批限制为 1–32 行，避免单次请求无限占用全局拓扑锁；更大集合分为用户明确提交的多批，每批分别给出完整结果。

原子提交遵循既有插件锁边界：

1. 认证并验证请求结构，对名称等字段进行与写入一致的规范化。
2. 开启事务，取得插件拓扑 advisory lock，检查同一 `request_id` 的已保存提交收据。
3. 按服务器 ID 排序取得全部入口与出口服务器锁，重验插件启用、协议、节点存在、独立入口、不同服务器以及循环/嵌套限制。
4. 校验整批端口，自动分配时将本批已分配端口也视为占用；任一非法项返回具体行号及原因。
5. 在同一事务写入全部入口、链路、内部凭据、幂等收据，并标记全部受影响服务器待发布；整批候选配置需通过现有编译校验。
6. 提交后返回收据 `request_id`、`chain_ids`、`entry_node_ids`，前端重新读取资源状态。写入任一步失败均回滚整批，前端不循环 POST 组合批量创建。

新增插件表 `singbox_chain_creation_requests` 保存 `request_id`、规范化请求摘要、结果 ID 收据和创建时间，不保存私钥。收据不随链路或入口删除级联清除。相同键、相同请求返回原收据；相同键、不同请求返回 409。删除资源后重放只返回原创建收据，资源查询显示已删除，不重新创建。前端网络超时保留提交键和原请求，用户修改草稿后生成新键，不能用新键自动重试原提交。现有 SHA-256 和 JSON 能力足够，不增加生产依赖。

## 授权、订阅与计量

授权对象是直连资源或链路资源。链路入口不能被单独授权，也不能通过普通 `node_ids` 绕过链路；这个限制同时保留在 API、数据库模型与编译器。多个策略组和原单独授权取并集，移除一个重叠来源不更换凭据，最后一个来源消失才撤销。

客户端只取得入口的用户凭据。内部 relay 身份由面板与两端运行时持有，不进入资源列表、详情或用户订阅。每条链路的用户流量在自己的入口计量，内部出口转发不再扣一次；同一出口上的直连用户仍正常计量。一个用户全部直连和链路入口共同使用自己的套餐额度，历史 `usage_records` 与计量 epoch 不因本次页面调整改变。

订阅沿用当前资格和两端配置应用检查。资源详情将这几个维度分别显示：

| 维度 | 展示规则 |
| --- | --- |
| 资源 | 完整 / 入口缺失 / 出口缺失 / 协议不匹配；旧破损链路仍可查看和清理 |
| 授权 | 未授权，或引用策略组及受影响用户数量；创建本身不授予权限 |
| 设备 | 分别显示两端在线或离线及观测时间 |
| 配置 | 未发布 / 等待入口应用 / 等待出口应用 / 应用失败 / 双端配置已就绪 |

“双端配置已就绪”表示健康且已应用目标版本，没有待发布变更。该状态不等于端到端探测成功。设备离线明确展示，已有订阅行为不在页面搬迁中偷偷改成新的连通性承诺。资源失效或配置不符合既有资格时不提供该链路，也不自动改为入口直连或直接连接出口。

## 编辑与删除

直连资源继续使用既有协议和证书能力。链路可修改显示名称、入口公开地址、端口和 SNI；入口协议、密钥、short ID、内部 relay 身份不通过本次编辑接口更改。影响运行配置的修改在一个事务内安排关联两端发布。旧入口名称与链路显示名称分开保存，改变订阅名称需明确操作，不能隐式改写用户正在使用的订阅投影。共享出口参数修改前展示所有受影响链路，保存后全部关联入口和出口重新发布。

入口、出口绑定继续不可变。更换出口采用“创建替代链路 → 明确调整策略组引用 → 等待新链路应用 → 清理旧链路”的流程。替代链路会有新的入口、端口和凭据，不承诺无损切换或自动继承旧授权。

删除链路资源前显示策略组引用与两端影响。仍有策略组引用时返回 409 和引用清单，先处理引用。资源删除在同一事务删除链路关系、软删除专用入口、清理入口授权并安排两端配置清理，保留历史计量；复用已有入口时，创建确认已明确其转为专用入口，删除规则相同。共享出口及其其他链路、直连用户保持。

删除作为出口的节点前检查全部依赖链路并返回 409 和清单，防止误删共享出口。core 的服务器退役仍沿用现有跨端撤销：相关链路显示资源缺失、退出资格并安排对端清理，不级联删掉其他服务器或绕链降级。旧兼容接口解除关系后若保留入口，不自动授权任何用户；这种操作不等同于新的资源删除。

统一删除接口与旧 `DELETE /nodes/{id}` 必须共用链路引用检查，不能只在新页面拦截。作为链路入口的节点要求通过链路资源删除，作为出口的节点要求先处理引用，均返回 409 和依赖清单。旧路由及请求形式保留，这项冲突规则加强对关联资源的保护；core 退役走前述失效与对端撤销流程。

破损链路的清理不能依赖“入口服务器仍存活”的创建校验。资源删除在插件锁之后按 ID 锁定关联服务器记录，允许其已经退役，再清理链路和入口，仅对尚未退役的对端安排发布；不能直接调用会排除退役服务器的 `lock_server` 使清理永远返回 404。资源已删除时返回明确的已删除结果，不重复退役其他节点。

本轮规划没有增加独立“停用链路”按钮。停用需要持久的启用状态与订阅、入口用户和出口 relay 的共同资格检查；如果之后实现，应单独验证，不能用只隐藏页面或订阅来模拟停用。

## 迁移与实施顺序

旧链路直接投影为链路资源，无需重新创建或改签配置。必须保留节点与链路 ID、两端关联、`relay_uuid`、用户 UUID 和 credential、`stat_name`、策略组引用、订阅 token / URL / 原名称、历史部署 `source_json` 及流量流水。已有链路入口从直连视图隐藏，已有破损链路保留。页签位置改变不产生生产数据迁移。

实施拆成三个可独立审查的阶段，最终交付以全部通过为准：

1. **统一资源读取与入口归位**：插件资源投影、节点列表/详情、策略选择器、服务器入口/出口角色展示。涉及 `plugins/singbox/panel/chains.rs`、`nodes.rs`、`mod.rs` 和 `web/src/plugins/singbox/{Nodes,Groups,ProxyUsers,ServerBusiness,UserEntitlements}.tsx`、`groupTypes.ts`、`web/src/types.ts`、`App.tsx`。
2. **创建与生命周期**：复用既有节点创建校验形成事务内服务，幂等迁移及原子批量创建、公开参数编辑、引用保护与资源删除；更新资源类型与中文交互。
3. **验收与说明**：PostgreSQL/编译器/真实浏览器验收，构建并提交 dist，更新实际 API 和使用说明；发布及生产迁移继续使用独立授权和既有流程。

实现须全程位于 sing-box 插件和已有编译器，不向 `agent-core` 添加代理资源模型或修改面板/Agent 公共协议；不新增运行时实例、任意拓扑或生产依赖。迁移编号在实施时从当时主线确定，不能占用其他进行中任务的编号。

## 必须通过的验收

| 场景 | 权威证据与通过标准 |
| --- | --- |
| 页面归属 | 桌面、手机和键盘浏览器操作：在代理节点创建、列出、查看、编辑及删除链路；策略页只有资源引用，无链路 CRUD |
| 多条链路 | PostgreSQL 和浏览器：同入口服务器创建三个出口对应三条链路、三个不同监听；资源列表和订阅各显示三项，无重复直连入口 |
| 原子失败 | 第二/第三项端口冲突、出口非法、编译失败及写入失败后，入口、链路、收据和 dirty 状态都无半批写入 |
| 并发与重试 | 两个请求争同端口、同一幂等键并发、超时重试、同键改内容、删除后重放；唯一创建且不复活已删除资源 |
| 拓扑边界 | API 与编译器拒绝非 Reality、同服务器、已授权入口、普通策略引用、重复入口、循环及嵌套；UI 候选提示覆盖同样场景 |
| 共享出口 | 两条链路和出口直连用户共存；删除一条只撤其专用入口/relay，另一条与直连用户继续使用；新旧节点删除接口都拒绝绕过依赖检查 |
| 授权并集 | 同链路被两个策略组授予；撤一个来源保持 UUID，撤最后来源移除资格与运行配置；单独入口授权无法绕过 |
| 双端应用 | 仅一端应用、部署失败或资源失效时不提供链路；配置就绪与真实连通分别核对；不出现直连降级 |
