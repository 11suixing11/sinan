# 延迟检测与通知

## 配置延迟检测

后台侧栏「延迟检测」进入 `/#/latency`，点击「添加任务」：填写名称、TCP/ICMP、目标地址、TCP 端口、10–3600 秒间隔和可选线路备注。目标支持主机名或 IPv4/IPv6，地址框不填写协议或路径。测量方向是服务器到目标，不是浏览器到服务器。

在服务器选择区搜索名称、地区或分组，逐台勾选或全选当前搜索结果。勾选「默认分配给新服务器」后，之后创建的服务器会自动获得此任务；对当前服务器的选择不会因此改变。可只保存为默认任务，也可只分配给现有节点。

保存后 Agent 通常在下一次配置刷新（约 30 秒）领取任务，再按间隔采样。未接入的服务器等待接入，已离线的服务器等待重新连接；保存成功不等于设备已执行。每轮 TCP 四次连接，显示延迟和连接失败率；ICMP 依赖系统工具及权限，显示延迟和丢包，工具或权限错误显示检测不可用。无权或失联期间，旧 Agent 配置最多保留一天，不能承诺离线节点立即停止。

统一任务和原「服务器详情 → 持续网络拨测」共存。每台服务器合计最多 32 个目标，批量修改有任一服务器超限则全部不保存。统一任务的副本只能在统一页面编辑；详情的「配置延迟检测」按钮可跳转。看板继续按每个实际目标展示结果与历史。

任务可暂停、恢复或删除。检测方式、目标和端口创建后固定，更换目标需新任务；名称、备注和间隔可编辑。取消分配后再分配会开始新历史，旧结果不会混入新测量。并发修改或有新服务器自动加入后，旧表单保存会提示刷新，避免误删分配。

管理员接口：

- `GET/POST /api/latency-tasks`
- `PATCH/DELETE /api/latency-tasks/{id}`
- 创建/修改体：`spec`（原 `ProbeSpec`）、`default_enabled`、`server_ids`；修改还需读取到的 `revision`。
- 分配到 Agent 的 API 与消息保持兼容，无需安装第二个探针程序。

## 配置通知

「看板与通知」包含全局通知开关、离线阈值、到期提前天数、流量提醒起点和资源规则。「告警通知」展示最近 200 条事件，可筛选离线、资源、到期、流量及未结束/已结束；关闭的事件保留 90 天。

- **离线**：默认 5 分钟，仅已上报过的设备参与；单节点的「离线告警」开关只控制该类型。恢复后发送恢复通知，面板重启保留等长宽限。
- **到期**：默认 0（关闭），可提前 1–365 天，每个到期日期提醒一次；开启时已过期不超过七天的记录可补提醒。自动续费只顺延资产记录，不付款。
- **流量**：默认 0（关闭），可设置 50–100% 的起始线，每增五个百分点提醒一次，最高 100%。例如设置 80%，依次提醒 80/85/90/95/100%；一次越过多条线会生成多个事件。按账单周期和配置范围去重，流量矫正后再次越线不会重复同一提醒。
- **资源**：最多 20 条规则，选择处理器、内存、磁盘使用率或上下行速度，设置阈值、1–1440 分钟窗口、判断方式及服务器范围。百分比为 0.01–100%，速率单位 MiB/s。全部服务器自动包含新节点；指定范围仅包含所选节点。

资源判断使用完整分钟的最后一次上报，窗口平均或每分钟都超限才触发；中间缺失、无效或服务器离线时保持原事件，不发送“已恢复”。采样晚到后可在后续评估中补齐当前窗口；这不是秒级连续性证明。面板每 30 秒评估，检测与通知均有延迟。网速遵循服务器的网卡筛选，内存/磁盘缺少容量时不判断。资源规则只提醒，不执行命令或停用服务。

全局关闭会结束当前事件并取消待发消息，历史仍可读。重新开启时按现状评估；到期和流量仍受去重收据约束。资源规则修改或删除会关闭旧事件、取消待发消息并保留历史。

管理员接口：`GET/POST /api/alert-rules`，`PATCH/DELETE /api/alert-rules/{id}`。创建/修改体为 `{ "spec": { ...规则字段 }, "revision": 读取到的版本 }`，新建省略修订号；`GET /api/notifications` 返回带 `category`、内容、判定详情及发送状态的历史。

## Telegram 渠道

填写机器人令牌与会话 ID，群组指定话题时再填写话题 ID。令牌只写不回显；留空保留，显式勾选清除才删除。话题留空回到默认会话。API 更新省略 `telegram_thread_id` 保留当前值，传 `0` 清空。

模板使用纯文本，支持 `{{title}}`、`{{server}}`、`{{message}}`、`{{time}}` 和 `{{event}}`。可先展开预览。只替换这些变量，不支持 HTML、Markdown 或表达式。建议保留事件编号；未知变量或不完整括号会拒绝保存。

先「保存设置」，再「发送测试通知」。测试接口 `POST /api/notifications/telegram/test` 使用已保存的机器人、会话、话题和模板，每 30 秒最多一次。测试不依赖自动通知开关，返回成功仅表示 Telegram 接受，请到接收会话确认。页面读取、保存设置和本地回归测试不会自动向真实会话发消息。

失败消息会自动重试，详情显示尝试次数及错误。切换机器人、接收会话、话题或关闭通知会取消旧待发消息。网络超时后无法完全判断远端是否已收件，可能重复；不能承诺恰好一次送达。接口根据 [Telegram 官方文档](https://core.telegram.org/bots/api#sendmessage) 实现。

迁移使用 `0019_latency_tasks.sql` 和 `0020_notification_rules.sql`；升级前照既有部署流程备份数据库。源码与本地回归不等于线上验收，本轮没有执行生产迁移、公开网络拨测、真实 Telegram 发送或多平台实机测试，CI 继续暂停。
