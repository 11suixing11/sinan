这是用户要求“开始下一步”后完成的第二个大步骤，处理[全仓缺陷扫描](defect-scan-20261003.md)中的 D5、D6、D7。工作在集成分支 `claude/sinan-scan-refactor-odrgr3` 上进行，起点是 main `f102a4f`（已合并第一步 PR #158）。设计见 [ADR 0077](../adr/0077-usage-daily-rollup-and-retention.md)。所有修改先集中完成并冻结，然后统一验证，最后提交一次。远端 CI 继续暂停，未触发、重跑或恢复。没有正式签署、发布、部署，也没有访问生产数据库或真实设备。

## 修改内容

- **迁移 `0049_usage_daily_rollup.sql`**（只追加，不改已有迁移）：
  - 新增按天汇总表 `singbox_usage_daily`；
  - 新增 `usage_records` 的语句级插入触发器；
  - 新增重建函数 `singbox_usage_daily_rebuild()`，迁移时用它回填历史；
  - 新增窗口求和函数 `singbox_usage_window`；
  - `singbox_entitlements` 签名和其余逻辑不变，只把周期用量改为调用窗口函数。
- **读取接口**：
  - 用量汇总接口（D5）和代理用户自助页的累计流量改读汇总表。
  - 统计页的完整日读汇总表，当天读明细，合并后再计算每日的用户数和节点数。
- **数据保留（D7 部分）**：维护循环每 30 秒执行一次，每类每次最多删除 500 行。
  - 删除过期超过 7 天的接入令牌。
  - 删除已结束超过 90 天的远程命令，但只删“结果已确认”或“从未被领取”的命令；每台服务器最近 100 条始终保留。
  - 两者都不清理：`deployments` 与账本 `usage_records`、`usage_batches`。理由见 ADR。
- **测试**：
  - 新增 `crates/panel/tests/usage_rollup.rs`：
    - 随机生成 400 多条明细，集中在日边界附近，跨 40 天，其中一条是 `u64::MAX`；同时重复写入。逐“用户×节点×日”核对汇总表与明细一致。
    - 用 200 多个随机窗口，加上对齐、空、倒置和负数边界，逐用户核对窗口函数与逐行求和一致。
    - 核对重建函数与触发器结果一致。
    - 用 +05:45 时区的套餐验证 `singbox_entitlements` 的周期边界：用量 1110，状态 `exhausted`；没有套餐的用户仍为 `0/unmetered`。
  - 新增两类保留规则的 PostgreSQL 单元测试，覆盖删除条件和保留条件。

## 统一验证

环境：本机 Rust 1.97.0，PostgreSQL 16.14（专用临时实例，回环 55432 端口）。

- `cargo fmt --check` 通过。
- 全工作区全 targets Clippy（warnings 视为错误）通过。
- `git diff --check` 通过。
- 分层检查 `tools/check-core-boundary.py` 通过。
- `sinan-panel` 全部 targets 共 69 组结果。首轮 547 通过、2 失败、7 条件忽略。两项失败是 `probe_leases`、`runtime_migration` 中写死“最新迁移为 48”的序列断言；以往每次新增迁移都会同步修改这两处，本次漏改。改为 49 后只重跑这两个目标，7 项全部通过。合计 549 通过、0 失败、7 条件忽略。其中包括新增的汇总与窗口用例、两类保留规则用例，以及原有统计、账本、套餐和迁移用例。其他 crate 没有改动，没有重复运行全工作区。
- **升级路径**：在独立库中只应用 0001–0048。
  - 灌入约 6 万条明细，跨约 70 天、20 个用户。

  - 原 `singbox_entitlements` 约 420 ms（冷启动 3.6 s），新版 9–26 ms，输出 md5 相同。
