# 节点 Netflix 错误判定验收

整体交付中的 #123 修复，产品提交 `3e7cbbb`，测试补修 `3388bc5`、`e5af119`。固定源的原函数把curl错误文本当成非空页面，403仍报告解锁；专用Debian提取原函数已复现，新版同一负对照显示未知。

r15固定查询helper分开处理curl退出码、HTTP状态与stdout；DNS、连接、TLS、超时、403、429、其他请求失败、空响应或无法识别/不一致的地区字段都不报告解锁。首个标题失败后停止，最多两个不同标题各一次请求，不重试。文本解释原因，JSON的Media.Netflix.Error与Attempts保留分类、目标IP、时间、curl耗时/退出码和HTTP状态；未知地区与类型保持空值。

合法200及一致地区字段仍进入原两标题启发式，不是实际播放或最新供应商页面契约的证明。没有调用公网Netflix或其它提供者；其余查询函数、cookies、公共授权材料及完整执行门禁保持原状。

新增6项专项在Debian全部通过，含真实curl到自有回环服务的403/429/超时、空与非预期200、第二次请求失败、旧错误负对照、已识别响应的既有判定、文本/JSON及摘要边界。DNS/连接/TLS使用明确惰性错误桩，未冒充公网故障。测试转发器只允许两个固定标题URL，改写到自有127.0.0.1，并仅在测试进程中缩短超时。

首次组合发现测试里的产物版本仍写r14（主机4错误、Debian3错误/另1签名条件跳过），以及报告编排惰性源码缺少新query锚点（主机2错误）。原日志保留，测试预期和锚点修复后只补跑失败与未执行套件；产品未更改。最终本机164个唯一用例144通过/20条件跳过，Debian128个唯一用例127通过/1缺minisign跳过。重复执行不作为新增用例。Rust/API19通过，adapter Clippy/fmt/core通过，Rust输入与最终测试提交逐文件相同。

两套Debian单元均读回256MiB/Swap0/Tasks64、CPU/IO10、OOM500、私有网络/挂载、control-group清理。峰值63,852,544B和69,861,376B，均无新OOM；结束无进程、挂载或cgroup，SSH未重启、同boot、swap0。各52份输入前后相同。专属PostgreSQL55439已停止并核实端口关闭。
