# 离线工厂容量与失败证据验收

本步骤在统一交付分支集中完成实现、测试代码和文档后冻结，没有中途测试。冻结后的失败保留原记录，修复后仅补验受影响或尚未执行的范围。决策和操作接口见 [ADR 0048](../adr/0065-nodequality-factory-capacity.md)、[工厂说明](../nodequality-rootfs-factory.md)，数值、原收据摘要及失败对应关系见[机器记录](evidence/nodequality-factory-capacity.json)。

## 实现范围

prepare、build、export 在创建新输出前分别计算副本、目录、块尾、展开树、APT 缓存/索引、归档、清单和临时/日志余量。默认本阶段输出预算 4 GiB，管理预留 512 MiB 和 1024 inode；既有缓存和先前输出已消耗的空间由每阶段实时 `statvfs` 反映，不能把同一份初始空闲量反复用于准入。

运行中检查新输出的逻辑字节、实际块、成员及实际可用字节/inode。复制和压缩收尾经过写前检查，子进程运行及关闭日志后的等待仍受检查。验签 scratch 放入本次输出。复制使用安全打开的单个普通文件 FD，增长/摘要不匹配拒绝；目录 FD、创建时身份和挂载检查保护遍历及清理。

原命令失败类型、已经观察的退出状态与有界输出保留到新的私有失败目录，清理结果单独记录；日志不是可执行指令。记录也保留管理空间，不足时附 note；确认输出清理后只能再尝试保存内存中的原日志，不重新执行命令。不改变原 prepared/build/export 收据字段、来源校验、builder 条件或设备 256 MiB 制品边界。

## 实际验收

基线为 `87efe43d511b9ed2e2736738df3c048e42970188` 加本步骤修改。最终冻结摘要为 `4ba4dea71e21e8fb89c60aabacb87cc6474e975225170954719799fa265af6c4`；622 个功能输入与最终记录一致。验收期间生产实现只在最后审阅补了日志 EOF 后的容量检查，其他修正限于夹具。

| 范围 | 最终不同方法结果 | 证据边界 |
| --- | --- | --- |
| Debian 12 原生 Python | 110 通过、0 未覆盖/条件跳过 | builder 34、capacity 43、collector 33；r4 的 4 项中 3 项重复不累计 |
| macOS Python及下游制品 | 110 通过、12 条件跳过 | builder 32、capacity 40、collector 26、artifact 12；这 12 个平台条件在 Linux 执行 |
| 跨平台去重 | 122 个方法最终通过 | 四个相关 Python 模块；不表示原整改所有实机能力通过 |
| 静态检查 | fmt、全 workspace/all-targets Clippy、core boundary、diff 通过 | 未重跑未改变的 Rust workspace 测试、前端构建或浏览器 |

专用 Debian 12 使用 256 MiB MemoryMax、swap 0、TasksMax 64、CPU/IO 权重 10、OOMScoreAdjust 500，独立网络和挂载命名空间，无外部路由。r2/r3/r4 峰值均小于内存限额，最高 235,753,472 字节；进程峰值最高 6，OOM 为零。各轮任务终止后，进程、挂载、cgroup 和临时目录清理读回通过，SSH PID/重启数与系统启动身份保持。

真实文件系统夹具只使用本次自有的 600 MiB sparse ext4 镜像和 2080 个 inode，实际核实 backing 文件、loop 关联与 mount 身份。写入生产者有独立 96 MiB/1400 文件上限，并逐次保护 backing 文件系统的管理预留：

- 磁盘场景：目标余量从 615,018,496 字节降至守卫观察的 518,774,784 字节，触发 536,870,912 字节预留阈值，生产者被 SIGKILL 回收；终态 backing 仍有 578,613,248 字节。
- inode 场景：可用 inode 从 2066 降至 990，触发 1024 预留阈值，生产者被回收；原 sentinel 文件保持。
- 两个场景最终均确认 PID 不存在、挂载消失、loop backing 关联解除、镜像和本次私有目录移除；外层另核实没有该次 loop 关联。

这验证主动停止保护，存在轮询间的超调。目标文件系统已经跌过阈值的事实保留，不能宣称零超调硬配额；没有用内核配额替代真实构建峰值。

## 真实材料的容量结果

在保留的实际 ARM64 `materials.json` 上只执行 schema 规划和实时容量读取，材料摘要前后仍为 `e5faa499e780e99b1c0dcd2c5c631f61a5379f320eff90f2cb2cc010bf696771`。没有重新认证正文、绑定 builder、复制材料或执行构建。

当前观测可用 675,377,152 字节。prepare 正文副本为 1,069,414,018 字节，含块/目录及临时余量的新增需求为 1,143,840,768 字节；build 保守新增需求 3,264,552,960 字节，export 为 318,832,640 字节。三阶段各自加上 512 MiB 预留后均拒绝，不能从小夹具通过推导这台机器具备实际工厂容量。旧缓存保留，没有扩 VM、删旧材料或改用生产节点。

## 原始失败与补验

冻结驱动首次误读旧私有清单字段，未启动产品验证；初始 shell 未包含 cargo 路径，使用实际安装路径后静态检查通过。两项原记录保留。

r1 旧 synthetic signed closure 没有 inert export 使用的 fixture 包，5 个方法产生 7 个子场景错误。补齐夹具的签名索引和锁，不放宽生产校验；r2 builder 34 项通过。r2 实际磁盘守卫成功停止生产者，但清理断言误把 util-linux 返回的已解绑设备行 `back-file=null` 当成残留；因失败暂存占用，后续 inode 场景条件跳过，collector 尚未运行。修正为核实 backing 关联已解除，r3 只补两个真实文件系统和 33 个未执行的 collector 方法，全部通过。原失败不改写为成功。

最后审阅发现显式 capacity 回调在子进程关闭日志后仍应继续检查。补齐等待循环，r4 只运行 4 个受影响的 Linux 进程方法，另在 macOS 执行新增的关闭日志回归；全部通过。首次失败、修正范围、冻结变化和每轮清理/资源记录分别保存。
